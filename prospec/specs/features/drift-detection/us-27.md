## US-27: knowledge-size ratchet fails growth of over-budget L1/L2 files [P0]

As a maintainer who gates CI with `prospec check --strict`,
I want a change that grows an already over-budget (or newly over-budget) L1/L2 knowledge file to fail `knowledge-size`,
so that knowledge files cannot keep growing silently, while existing overage need not be paid off in a single change.

**Acceptance Scenarios:**
- WHEN the ratchet is enabled and an L1 or L2 file that was over budget at the merge-base is now larger in tokens (or, for L2, lines), THEN `knowledge-size` reports FAIL naming the merge-base value, the current value and the budget, and `--strict` exits 1
- WHEN that file's size is unchanged or smaller, THEN it still reports WARN, as before
- WHEN an L1/L2 file was absent or within budget at the merge-base and is over budget now, THEN it reports FAIL
- WHEN `.prospec.yaml` has no ratchet setting, THEN the `knowledge-size` findings are identical to those before the ratchet existed, all WARN
- WHEN the ratchet is enabled and a Demand, Feature Spec, skill or reference file grows, THEN it still reports WARN only
- WHEN the configured base ref does not exist or has no common ancestor with HEAD (for example a shallow clone), THEN `knowledge-size` reports FAIL explaining the reason and the fix
- WHEN the project is not a git repository and the ratchet is configured, THEN it also reports FAIL, never WARN, PASS or skipped
- WHEN an unchanged file's merge-base path passes through a submodule or a symlink, or differs only in directory case on a case-insensitive checkout, THEN it keeps its WARN instead of failing as new debt
- WHEN an agent follows `prospec-knowledge-update` or `prospec-knowledge-generate` with the ratchet enabled, THEN it keeps an over-budget L1/L2 file no larger than at the merge-base
- WHEN `core.autocrlf` converts a file's line endings, THEN line endings alone never make it fail or hide its growth, and a new or renamed path fails as absent at the merge-base rather than as grown

#### REQ-TYPES-118: knowledge.size_ratchet config and the ratchet finding fields
`KnowledgeSchema` declares an optional `size_ratchet` key whose value the schema accepts in any shape: REQ-LIB-111 reads its `base` — the git ref the ratchet compares against — and grades any other shape, an empty base, or a base git would read as an option as unresolvable, so a mistyped ratchet fails the knowledge-size check instead of making every command that reads the config fail. It lives beside `token_budget`, not inside it, so `TokenBudgetSchema`'s key set and REQ-TYPES-061's key-set contract are unchanged. `KnowledgeSizeFindingSchema` gains three optional fields, present only on an over-tier finding of a ratchet-governed item while the ratchet is resolved: `base_commit` (the merge-base commit) on every such finding, plus either `base_actual` — the same unit's value at the merge-base, or `null` when the file did not exist there — or `ratchet_skipped`, the reason the ratchet was not applied to that file. A report without them still validates.
- WHEN `.prospec.yaml` omits `knowledge.size_ratchet`, THEN the config validates and the ratchet is off
- WHEN `knowledge.size_ratchet` is not a mapping, or its `base` is missing, empty, not a string or starts with `-`, THEN the config still validates and REQ-LIB-111 reports the ratchet unresolvable
- WHEN a report's knowledge-size finding carries none of `base_commit`, `base_actual` or `ratchet_skipped`, THEN it still parses through `DriftReportSchema`

#### REQ-LIB-111: knowledge-size ratchet against the merge-base
When the knowledge base exists and `knowledge.size_ratchet` is present, `collectKnowledgeSize` validates its shape and resolves `git merge-base <base> HEAD` in the project directory and measures at that commit every item that is over a budget now — by the one `overBudgetUnits` predicate the evaluator also grades with — and whose kind's `KNOWLEDGE_SIZE_RULES` entry declares `ratchet: true` (`l1` and `l2`), reading the blob through `git cat-file --filters` so the base text has the same filter conversion as a checkout, and comparing it with the current file after removing every carriage return from both texts, so that neither `core.autocrlf` direction reads an unchanged file as grown or hides real growth, and a unit fails only when that carriage-return-free size is itself over the budget; both sides use the same `estimateTokens` / `countLines`, the finding's `actual` stays the unnormalized current measurement and `base_actual` is the normalized merge-base value. When `core.ignorecase` is true, an item's path is looked up at the merge-base under its one case-insensitive match in the index — read under the caller's repository selection (`GIT_DIR`, `GIT_WORK_TREE` and `GIT_INDEX_FILE` are kept; only the pathspec-mode variables are cleared) — so a directory renamed only in case on disk is compared with its committed self; more than one such match leaves the item unratcheted with `ratchet_skipped` naming the ambiguity, and an untracked item keeps its working-tree path; when `core.ignorecase` is not true the working-tree path is used as is. Only a regular-file entry (mode `100644` or `100755`) is measured. A path absent from the merge-base tree is recorded as absent, never as size zero — unless one of its ancestor paths is a gitlink or a symlink at the merge-base, whose contents the merge-base tree does not hold. A path that is not a regular file at the merge-base, that passes through a gitlink or symlink there, or that is or passes through a symlink in the working tree, is not ratcheted, and its finding carries `ratchet_skipped` naming that reason. `evaluateKnowledgeSize` then grades each budget unit (tokens, and lines where the rule has a `lineKey`) of a ratchet-governed item independently: a unit over its budget whose merge-base value is absent or smaller than the current value is a `fail` finding whose detail names the merge-base commit, the current value, the budget and the kind's remedy, plus the merge-base value when the path existed there or, when it did not, that the path is absent at the merge-base — a new or renamed path, never described as grown — and whose `knowledge_size` carries `base_commit` and `base_actual`; every other over-budget unit keeps its existing warn finding, with `base_commit` and `base_actual` (or `ratchet_skipped`) added. A configured ratchet that cannot be resolved — a `size_ratchet` value that is not a mapping, a `base` that is missing, empty, not a string or starting with `-`, not a git work tree, a shallow clone or a failed shallow probe, an unknown ref, no common ancestor, a failed tree, index, config or blob read, or any of these git reads exceeding 30 seconds — makes the source's ratchet unresolvable, keeps every item and its existing warn grading, and adds one `fail` finding on `.prospec.yaml` naming the base, the reason and the fix for that reason's class: correcting `knowledge.size_ratchet.base` for a malformed value, fetching full history (`fetch-depth: 0`) for a shallow clone, both — plus re-running, since a failed or timed-out `git merge-base` reads the same as a missing one — for a base with no merge-base, and re-running inside a git work tree whose objects git can read for every other cause. That finding carries no `knowledge_size` object because it measures no file; it is never reported as warn, pass or skipped, because `--strict` does not fail on a skipped check; an absent knowledge base still skips the whole check first, ratchet or not.
- WHEN the ratchet is configured and an over-budget L1 or L2 file's tokens exceed its merge-base tokens, THEN the knowledge-size check reports a fail finding with `base_actual` and `--strict` exits 1
- WHEN the same file's size is equal to or smaller than at the merge-base, THEN it keeps the warn finding it has today
- WHEN an L1 or L2 file is absent at the merge-base, or was within budget there, and is over budget now, THEN it reports fail
- WHEN only an L2 file's line count grew past both its merge-base count and the line budget, THEN the line finding is fail and the token finding is graded on its own
- WHEN a `spec`, `demand-knowledge`, `skill` or `reference` file grows while over budget, THEN it reports warn only
- WHEN the configured ratchet cannot be resolved, THEN one fail finding on `.prospec.yaml` names the reason and the item findings stay warn without ratchet fields
- WHEN the ratchet is not configured, THEN the knowledge-size findings are identical to those produced without this requirement
- WHEN the working tree uses CRLF through `core.autocrlf` and the committed blob uses LF, THEN an unchanged file is not reported as grown
- WHEN a ratchet-governed file is a symlink, THEN it keeps the warn grading and its finding carries `ratchet_skipped` instead of `base_actual`
- WHEN an over-budget file's path at the merge-base passes through a gitlink or a symlink, or is not a regular file there, THEN it keeps the warn grading and its finding carries `ratchet_skipped` naming that path
- WHEN `core.ignorecase` is true and a file's directory differs from the index only in case, THEN the file is measured at the merge-base under its index path
- WHEN `core.ignorecase` is true and more than one index path matches a file case-insensitively, THEN it keeps the warn grading and its finding carries `ratchet_skipped`
- WHEN `core.ignorecase` is not true, THEN the merge-base lookup uses the working-tree path with its exact case
- WHEN the unresolvable cause is a malformed `size_ratchet` value, THEN the fix names `knowledge.size_ratchet.base` and not `fetch-depth`
- WHEN the unresolvable cause is a shallow clone, THEN the fix names `fetch-depth: 0` and not `knowledge.size_ratchet.base`
- WHEN the base has no merge-base with HEAD, THEN the fix names both `knowledge.size_ratchet.base` and `fetch-depth: 0` and suggests re-running
- WHEN the unresolvable cause is not a git work tree or a failed or timed-out git read, THEN the fix asks to re-run inside a git work tree whose objects git can read and does not name `fetch-depth`
- WHEN `core.autocrlf=input` and an unchanged over-budget L1 or L2 file is saved with CRLF line endings, THEN it keeps the warn finding
- WHEN `core.autocrlf=true` and an over-budget L1 or L2 file written with LF line endings grew past its merge-base content, THEN it reports fail
- WHEN an L1 or L2 file is over budget only by its carriage returns, THEN it keeps the warn finding
- WHEN an over-budget L1 or L2 file is absent at the merge-base, THEN its fail detail says the path is absent at the merge-base and does not say it grew
- WHEN `GIT_DIR` and `GIT_WORK_TREE` select the repository and `core.ignorecase` is true, THEN the ratchet measures the over-budget files instead of reporting the ratchet unresolvable
- WHEN the inherited environment sets `GIT_LITERAL_PATHSPECS=1` and `core.ignorecase` is true, THEN the case-insensitive index lookup still resolves a directory that differs only in case

#### REQ-TEMPLATES-274: the ratchet is documented where users configure and read it
`src/templates/references/config-example.yaml.hbs` declares `knowledge.size_ratchet.base` with a comment stating that the ratchet is off when the key is absent, that it fails an over-budget L1/L2 file that grew past its merge-base size, that CI needs full git history, and that a renamed, untracked or ignored L1/L2 file is new at the merge-base and therefore fails whenever it is over budget. `src/templates/skills/references/drift-report-format.hbs` documents the `knowledge_size` fields `base_commit`, `base_actual` and `ratchet_skipped` — including that a path passing through a gitlink or symlink at the merge-base, or not a regular file there, is skipped — the conditions under which `knowledge-size` reports fail, and that the unresolvable-ratchet finding carries no `knowledge_size` and names the fix for its cause.
- WHEN a user runs `prospec config example`, THEN the output shows `knowledge.size_ratchet.base` and parses through `ProspecConfigSchema`
- WHEN an agent reads the drift report format reference, THEN it learns which knowledge-size findings can be fail and what `base_commit`, `base_actual` and `ratchet_skipped` mean

#### REQ-TESTS-148: knowledge-size ratchet tests
Pure unit tests cover every REQ-LIB-111 grading scenario and are mutation-verified (turning the fail back into warn turns them red); an integration test over a real git repository covers merge-base measurement, a project in a repository subdirectory, a CRLF working tree, a symlinked knowledge file, an ancestor that is a gitlink or a symlink at the merge-base, an exact path that is not a regular file there, a directory that differs from the index only in case under `core.ignorecase=true` (set explicitly, so the case runs on every filesystem) together with the ambiguous and `core.ignorecase=false` counterparts, a new file under a directory that exists at the merge-base, an unchanged CRLF file under `core.autocrlf=input` and a grown LF file under `core.autocrlf=true`, a renamed path's fail detail, a repository selected through `GIT_DIR` and `GIT_WORK_TREE`, a case-insensitive lookup under an inherited `GIT_LITERAL_PATHSPECS=1`, and each unresolvable cause (no git, shallow clone, unknown ref, a base with no common ancestor). Collector-level tests cover each malformed `size_ratchet` value and each failed read — the tree read, the ancestor tree read, the case-insensitive index read and the `core.ignorecase` probe — asserting the reason, that no git read follows a malformed value, and the fix the evaluator names; they also assert the cause of each unresolvable class (`config`, `history`, `ref`, `environment`) and pass the collector's result to the evaluator. A contract test pins the rendered size of the downstream `index.md` the loading-rules partial renders into. Every git-bound test file declares a file-level `testTimeout`, and the integration test runs git through the shared fixture that disables commit signing and background maintenance.
- WHEN the ratchet's growth comparison is reverted to always-warn, THEN the unit suite fails
- WHEN the collector reads a base path relative to the repository root instead of the project directory, THEN the subdirectory integration case fails
- WHEN a not-found path is recorded as absent without consulting its ancestors, THEN the gitlink and symlink-ancestor integration cases fail
- WHEN the leading-`-` check on `size_ratchet.base` is removed, THEN a collector test fails
- WHEN the merge-base lookup treats any ancestor that exists at the merge-base as a link, THEN the new-file-under-an-existing-directory integration case fails
- WHEN the collector classifies a shallow clone or a missing merge-base under another cause, THEN a collector test fails
- WHEN the loading-rules partial grows, in any wording, THEN the contract test fails

#### REQ-TEMPLATES-275: knowledge skills keep an over-budget L1/L2 file from growing
When `.prospec.yaml` sets `knowledge.size_ratchet`, `prospec-knowledge-update` and `prospec-knowledge-generate` treat an L1/L2 file that is already over budget as capped at its size at the merge-base of `knowledge.size_ratchet.base` and HEAD; without it they keep their existing budget guidance. Their sub-module and overflow steps and their Error Handling tables state that such a file may not end larger than at the merge-base, that new content is offset by extracting a sub-module or deleting duplicated text, that growth caused by a new `## Sub-Modules` link or by regenerating `index.md` from a curated module map must be offset in that same file, that a newly created L1/L2 file — an extracted sub-module included — has no merge-base size and must be created within its budget, and that `prospec check`'s `knowledge-size` result is the self-check.
- WHEN `knowledge.size_ratchet` is set and an agent following either skill adds content to an L1/L2 file that was over budget at the merge-base, THEN the skill tells it to keep the file no larger than at the merge-base by extracting a sub-module or deleting duplication
- WHEN the addition is a `## Sub-Modules` link in an over-budget parent README, or a module-map curation that regenerates an over-budget `index.md`, THEN the skill tells it to offset that growth in the same file
- WHEN the skill extracts a new sub-module, THEN it tells the agent to keep that new file within its budget
- WHEN a skill's README-overflow Error Handling row applies to a file already over budget, THEN it points to this rule instead of "trim until within budget"
